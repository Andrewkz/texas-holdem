# Design

## Context

变更动机见 `proposal.md` 的 Why。本设计只落实既有路线图与一期计划中的顺畅入场、原座位恢复和手机操作，不把规划中的账本或持久化当作已实现能力。

提案形成时的基线检查得到以下实现约束（实施结果见验收报告）：

- `assets/scripts/bootstrap/GameBootstrap.ts` 同时构建 Cocos 界面、管理入口和播放动画。启动先显示首页；`openOnlineSetup()` 读取本地凭证用于表单预填，没有页面刷新自动恢复入口。
- `assets/scripts/net/OnlineCredentials.ts` 已使用“查询参数 → 已保存 endpoint → 远程页面同源 `/ws` → 本机 2567 默认”的选择顺序。部署由 Nginx 提供 `site/` 并代理 `/ws`，不能让邀请无意继承其他服务器的旧记录。
- `NetClient.ts` 对消息和打开事件已有 socket 对象检查，但旧 `onclose` 仍会调用当前 `onClose`；连接建立和 `joined` 等待尚无完整超时控制。`OnlineSession.ts` 默认重试 5 次，渲染更新通过 Promise 队列串行执行。
- `server/src/RoomManager.ts` 在加入成功后发送 `joined`，普通加入没有补发进行中牌桌快照；重连路径会补发。`Room.ts.broadcastStateSync()` 当前广播共享快照，合法动作没有按接收者过滤。
- `Room.ts` 每手重建引擎并维护房间手号。引擎玩家列表可能包含零筹码未发牌者，当前客户端却按大厅成员及筹码生成背牌；全压后筹码为零也不能证明玩家没有参与该手。
- 默认保座常量仍为 60 秒，行动超时为 30 秒；房主离开后当前选择剩余列表首人，不保证其在线。房间、身份及牌局仅在服务端内存中，房间码可能复用。
- 当前视图以 1280 × 720 设计画布和网页 16:9 外壳等比缩放。设计坐标中的按钮高度不能证明手机上达到 44 CSS px；真机 Safari、Android Chrome 的键盘、前后台和网络恢复尚未验收。

## Goals / Non-Goals

**Goals:**

- 在现有 Cocos、Node 单进程与 WebSocket 边界内，把入口决策、连接生命周期、接收者权限和视口计算变成可独立验证的小模块。
- 用服务器权威身份及状态恢复同一座位，所有成功、拒绝、超时、取消和接管路径都有有限且可见的结果。
- 让实际发牌名单、本人参与状态与行动权限由服务器明确提供，首次加入、正常推送和重连共用同一过滤逻辑。
- 为不兼容的协议变更建立明确版本握手，混合版本不能进入牌局后才因缺字段失败。
- 验证实际 Cocos 构建包及手机横屏操作，保留桌面与原单机 AI 模式。

**Non-Goals:**

- 不引入新数据库、外部状态服务或运行时依赖，不修改扑克引擎的洗牌、盲注、底池和边池算法。
- 不实施补码、账本、稳定整场参与者身份、正式结束本场、全员断线后的持久结算、服务器重启恢复或 30 天结算分享。
- 不新增账号、联机 AI、自定义盲注、公开匹配、独立观战或排行榜；不通过等待下一手界面扩大参与权限。
- 规划本身不授予执行权限；本变更已按用户后续授权进入实现与验收，生产连接、部署或房间操作仍需相应发布授权。视觉工作沿用已有风格，无需图片生成或整站重新设计。

## Decisions

### 1. 入口决策与渲染接线分离

新增 `assets/scripts/net/RoomInvite.ts` 处理房间码与邀请 URL，新增 `OnlineEntry.ts` 根据邀请、保存凭证和目标 endpoint 返回恢复、加入或设置意图；`HomeFlow.ts` 管理恢复画面及返回路径，`GameBootstrap.ts` 只接线意图、状态通知和渲染。新增 `assets/scripts/ui/PokerViewport.ts` 做纯视口计算，复用现有 `SessionGeneration.ts` 的失效机制。

不再向 Bootstrap 添加一组相互依赖的 URL、凭证和网络判断，因为纯决策模块可以在无 Cocos 环境中验证。也不引入新的框架或统一状态库；当前状态规模用明确类型、现有状态机和会话代号即可表达。

### 2. 邀请确定目标，保存凭证只证明本人身份

`RoomInvite` 生成当前站点路径下的 `?room=AB23`，保留部署路径前缀，清除原有查询参数与 fragment。房间码按现有四位字符表 trim、转大写、验证；不复制 `server`、token、昵称或存储内容。浏览器原生分享不可用或未成功时，提供复制或可选择的链接文本；HTTP 环境不能依赖安全上下文才可用的剪贴板 API。

解析结果区分“缺少邀请”“有效邀请”“显式无效邀请”，不能都压成 `null`；这是对原计划建议接口的实施细化。有 `room` 参数但为空、非法或歧义重复时，显示邀请无效，不自动恢复本机原房间，也不悄悄忽略参数。只有没有邀请时才采用普通入口的恢复决策。

有有效邀请时，先按站点部署配置或同源 WebSocket `/ws` 确定 endpoint，本机开发使用既有 2567 默认。旧保存地址及任意 `?server=` 不得覆盖邀请目标；部署若无法确定邀请后端，显示不支持该邀请，不尝试其他服务器。无邀请的普通联机入口保持现有地址优先级，避免破坏手工配置用例。

比较 endpoint 时规范化 WebSocket URL，并比较完整协议、主机、有效端口、路径和有意义的查询参数，不能只比较 hostname。邀请房间不同或 endpoint 不匹配时不发送旧 token。身份恢复必须使用 `reconnect`；不能因为房间码相同就认为是同一场，更不能按昵称恢复。旧房间销毁后即使房间码复用，原 token 仍应被拒绝；本期不新增稳定整场 ID 或跨进程恢复承诺。

恢复失败展示“原座位无法恢复，可重新加入”，等待用户明确操作；不得自动发送 `joinRoom` / `createRoom` 或再次发放首次筹码。断线、刷新与取消本次恢复不删除凭证；主动离房或明确放弃原身份时只清理对应记录。替代方案“所有入口优先保存地址”会把好友邀请导向别的服务器；“失败就新加入”会制造重复玩家，因此均不采用。

### 3. 每个连接先协商协议，再执行入场

这次 `handStart.participantIds` 和 `stateSync.participation` 是必填契约，按不兼容协议版本处理。在 `protocol.ts` 定义统一 `protocolVersion = 2`：socket 打开后，客户端先发送 `{ type: 'hello', protocolVersion: 2 }`，服务端校验后回复相同版本的 `hello`。每个新 socket 只协商一次，重连建立新 socket 时重新协商，不给每条业务消息重复加版本。

服务端连接状态记录是否协商成功；未成功或版本不匹配时拒绝创建、加入、恢复、开始及行动请求，返回 `protocol-mismatch` 和刷新/升级提示，不修改任何房间。新版客户端在收到匹配回应前不发送 token 或业务入场消息。旧服务端对 `hello` 返回 `bad-message`、回应版本不同、回应格式无效或握手超时，都进入明确的版本不兼容结果，不用缺少字段的消息驱动渲染，不进行无尽重试或静默新加入。旧客户端向新版服务端直接发入场请求时也会收到清楚的升级错误。

为必填字段建立运行时解析与校验，不能继续只依赖 `JSON.parse(...) as ServerMessage`。握手成功后仍需校验消息形状，非法推送不能进入状态机或动画层。

这是把原计划中“前后端同版本交付”落实为可观察错误的工程细化，不新增产品玩法。替代方案“部署时总能同时刷新所有浏览器”无法覆盖旧标签页、缓存和滚动发布，因此不采用；也不维护两套长期兼容协议。

### 4. 服务端统一生成每位接收者的牌桌快照

在 `Room.ts` 收口一个按玩家生成并发送状态的方法，供加入补发、重连补发和每次行动后的正常广播共用。保留 `stateSync.snapshot: EngineSnapshot`，新增本人 `participation: 'playing-hand' | 'waiting-next-hand'`。只有本手已发牌且确实轮到自己的接收者收到合法动作，其余接收者一律 `legalActions=[]`。已弃牌玩家仍属于本手发牌者，但没有行动权；中途加入或未获发牌者持续处于等待状态。

`handStart` 增加冻结的 `participantIds`，来源为开手后实际获得两张底牌的玩家 ID，保存到房间当前手状态。不使用整个 `snapshot.players`、大厅列表或推送瞬间筹码判定：零筹码未发牌座位不在名单，而已发牌后全压至零的玩家仍在名单。开局即结算的双盲全压也必须从该手真实发牌结果得到名单。

客户端仅按名单创建本手背牌；`yourHand` 只发给本手本人，不向等待者发送空牌来模拟参与，更不从大厅成员合成本人手牌。等待者立即看见公共牌、筹码与“已入座，下一手加入”，以后每次推送仍保持等待和空动作，直到新手实际发牌名单包含其 ID。公共状态不包含未公开的他人手牌。

本手身份映射不能仅来源于当前 `roomState.seats`：离座者可能已被大厅移除，却仍在本手引擎快照和后续事件中。利用冻结发牌名单与快照中的公开玩家 ID/名称维护本手映射，手内不复用离座者的牌张显示槽给新等待者；缺失大厅记录不能降级为原始服务端 ID 并传给固定节点映射。新加入者若不在本手名单，以独立等待提示呈现本人，必要时当前手按冻结参与者展示全部六个位置，到下一手才重新布局本人底部座位。三人局离座后加入、满桌空位换人均须覆盖，不增加独立观战产品。

邀请生成前还需比较当前连接的实际 endpoint 与站点部署目标。纯 URL 清洗即使能产生同站链接，也不能证明它仍能加入当前房间；不一致时必须明确提示无法生成该后端邀请。

相比仅修补 `resendHandState()`，统一入口可避免第三人刚加入时正确、其他人行动后又错误获得动作的回归；服务端行动校验仍是最终权威，客户端隐藏按钮不是权限控制。

### 5. 先确认身份，再交付补发与动画

`RoomManager.joinRoom()` 与重连路径保证对新连接先发送 `joined`，之后才发送该连接的 `handStart`、本人 `yourHand` 和过滤后的 `stateSync`。`Room.addPlayer()` / `reconnectPlayer()` 可能触发的成员广播不得在该连接身份确认前驱动其牌桌；可先排除新连接，再统一补发，或将广播延后，最终顺序必须相同。

Bootstrap 收到 `joined` 后同步建立 `OnlineSession`、初始化座位映射并接管后续消息，之后才播放页面转场；不能等待转场结束再绑定监听器。正在等待下一手者只补适用公共状态，不为了套用恢复流程制造发牌。房间回到大厅时使旧牌桌代号失效，清理公共牌、本人牌、动作及挂起动画，不继续显示上一手可操作状态。

快照是权威状态，动画是可取消的呈现。在连接恢复成功、切换房间、回大厅、主动离房或接管失效时递增会话/渲染代号；每项排队更新及每个 `await` 之后都检查“房间标识 + 连接代号 + 手号”，不能仅比较可能在新房间重复的手号。恢复快照重建当前画面时，旧 Promise 队列、发牌 tween 或迟到回包不能随后覆盖新状态；仅在“开始动画前”检查一次不足以防止覆盖。收到 `joined` 只代表身份确认，必须等新的权威快照实际应用到界面后才可恢复行动按钮。

### 6. 180 秒保座与 30 秒行动分开计时

把 `RECONNECT_WINDOW_MS` 改为 `180_000`，服务端在识别当前绑定连接断开时建立该座位的权威过期期限。重复关闭通知不延长期限；恢复校验同时比较服务端当前时刻与期限，达到或超过期限即拒绝，不依赖 timer 是否因事件循环延迟而已经执行。客户端重试预算不决定座位是否有效；刷新页面也不能重置服务端期限。行动计时仍为 30 秒，能过牌则过牌，否则弃牌；恢复不调用会重置当前行动 timer 的逻辑，不提供缺少服务端截止时间依据的精确倒计时。

重复 close 只处理当前绑定连接一次。替换连接后，旧连接的迟到 close 不得把新连接座位标为离线；服务端需要比较连接归属并取消旧保座 timer，timer 回调同样校验当前连接代号/断线代号，不能仅通过 playerId 操作后来恢复的玩家。`NetClient` 的旧 socket close 不得触发新 socket 的 `onClose` 或清空它。

房主明确主动离开时，在有效剩余座位中按既有座位顺序选择在线接任者；没有在线候选者时显式保留待接任状态，由保座期内首位有效恢复者接任。短暂断线不等于主动离开，也不随机把房主权交给离线玩家。

本期仅延长座位保留、补齐接任与内存状态处理；全员断线 3 分钟后的正式散场结算及跨重启等待状态仍属于后续阶段，不能提前宣称已经完整交付。

### 7. 有限重试、有限确认等待和终止状态

连接控制由 `NetClient` 的单次 socket 生命周期和 `OnlineSession` 的恢复生命周期分担：每次尝试包含 socket 建立、版本握手及等待 `joined` 三个有界步骤，分别采用 10 秒、5 秒、10 秒上限；统一恢复周期另设本地最多 180 秒预算和最多 20 次尝试，以先达到者为准。退避从 2 秒增长至最多 15 秒，允许小幅抖动，所有等待不得越过总预算。具体常量集中定义、可在测试中缩短，不引入新依赖。

超时关闭本次 socket，再决定是否进入下一尝试；收到服务端明确的座位拒绝、版本不兼容或 `session-taken-over` 时终止重试，不能将它当作普通网络波动。自动恢复失败不删除凭证或自动新增玩家。取消、主动离房、切换入口和旧标签页被接管立即失效当前代号，清除连接、握手、确认和退避 timer；异步回包必须同时匹配当前 socket 与恢复代号。

连接状态以 `connecting`、`restoring`、`connected`、`reconnecting`、`resume-unavailable`、`session-taken-over` 等明确类型通知 UI。等待连接时禁用重复提交和行动；网络断开后不重放未确认的出牌，恢复后以服务器快照为准。客户端 180 秒只是本地停止等待的上限，界面不能将它显示为服务端剩余保座的准确倒计时。

替代方案“只限制重试次数”挡不住一次连接或一次 `joined` 永久悬挂；“只加总超时”又容易遗漏取消后的回包，故采用阶段超时、总预算和代号共同约束。

### 8. 按实际 CSS 尺寸布局和验收

`PokerViewport` 输入扣除安全区后的实际可用 CSS 宽高，输出逻辑画布尺寸、操作区高度及紧凑模式。桌面保留 1280 × 720 基准，手机横屏允许调整逻辑高度和操作区，卡牌、座位和公共区一起计算；网页模板通过布局参数配合实际画布比例，不能强制以原 16:9 外框裁切新的逻辑高度。

主要动作、确认、取消及入场操作的实际可点击高度至少为 44 CSS px；以画布渲染后的 CSS 边界和逻辑缩放比例计算，并在实际构建中测量。设备像素比或高分辨率 framebuffer 不计作 CSS 尺寸，单测中逻辑 `actionHeight >= 44` 不能替代实际触控验收。对 844×390、667×375、1280×720、1440×900 等视口验证无负尺寸、遮挡和重叠；竖屏提供非阻断提示，不把它计为横屏验收。

键盘展开、收起、旋转与安全区变化触发重新计算，监听器卸载成对。昵称/加注输入和弹层采用能适应高度变化的排布或明确滚动，不让确认/取消落在不可见区域；模态层继续阻止点击穿透。保留 Cocos 原生 EditBox 的正常编辑生命周期及足够的 endpoint 长度，新增字符串处理符合现有编译目标，生成对应 `.meta`。

不用图片资产或全面视觉重设计解决这些问题：关键是可见空间、交互反馈和触摸尺寸。2026-10-17 用户明确要求“直接在浏览器做校验即可”，因此本阶段以实际 Cocos 构建包的浏览器流程与模拟手机视口验收：覆盖原生 EditBox 输入、缩小可视区域模拟键盘、旋转、模拟安全区、页面冻结/恢复及断网恢复。记录浏览器版本、URL、构建标识、失败资源和页面错误；系统键盘、设备安全区与操作系统后台行为不属于已验证范围，也不再作为本阶段完成前置条件。

## Risks / Trade-offs

- 协议升级会使旧标签页不能继续入桌 → 先握手、明确刷新提示、业务请求协商前拒绝；前后端成套验收和发布，不宣称混合兼容。
- 单进程内存状态仍会在服务重启时丢失 → 一期文案与交付记录明确限制，凭证拒绝后不静默新加入；不把本地 token 当作持久恢复保证。
- 部署 endpoint、旧保存地址或复用房间码混淆身份 → 有邀请先确定站点目标，再按完整 endpoint 匹配凭证；token 不进入链接、日志或公共推送。
- 按接收者构造快照可能有一条广播路径遗漏 → 所有正常推送与补发收口，测试连续行动后的等待状态和动作隔离，而非只测首次加入。
- 重连、旧 socket 关闭与动画串行队列存在竞态 → 服务端连接归属检查，客户端 socket/会话/渲染代号并用；通过假时钟和受控异步序列覆盖迟到事件。
- 手机后台可能暂停 JavaScript 和 WebSocket → 服务端权威过期；回前台复查状态，不依赖本地动画计时恢复牌局。
- 自适应画布可能影响桌面、单机与 Cocos 编辑/构建路径 → 纯布局计算测试加最终构建包检查；保留单机回归，不以源码单测代替渲染验证。
- 浏览器模拟不能覆盖设备系统行为 → 报告明确模拟与未测边界；按用户最新决定以浏览器验收，但不降低 44 CSS px、完整 2–6 人流程、输入与恢复结果要求。

## Migration Plan

1. 实现阶段先补协议与生命周期回归测试，再实现入口纯模块及服务端接收者快照，随后接线状态机与手机布局。旧一期计划中的协议同版本要求由上述握手补充落实，相关规格和任务同步采用此决定。
2. 本地同时更新客户端和服务端的协议常量、类型、解析器及测试夹具；无存储 schema 迁移，无新外部依赖。依次运行游戏/服务端类型检查和完整测试。
3. 用 Cocos Creator 3.8.8 与仓库 `build-templates/web-desktop/` 生成真实 `site/`，确认对应构建 Finished、生成包与源实现一致；在独立本地端口验证多人加入、恢复、接管、等待、回大厅、混合版本拒绝与手机尺寸。
4. 按用户2026-10-17的决定，在浏览器中完成手机视口、输入、旋转、模拟安全区、页面冻结/恢复与网络恢复验证。测试证据置于仓库外，记录访问地址、构建标识、浏览器版本、模拟条件和失败/未测项；仅在浏览器验收通过后提交一期完成结论，不声称已做真实手机验证。
5. 未来生产发布必须另获该次发布授权；发布前检查在线房间并说明无持久化重启会影响在局玩家，保存可回退的客户端与服务端配套版本。协调更新前端静态包与服务端，避免只发布一端；版本握手只能给出清晰失败，不能消除发布时已有对局中断。
6. 未来获授权的发布若烟测失败，回退整套匹配版本并让客户端刷新；不能仅回退其中一端。当前规划不执行生产连接、房间操作、重启或部署。
